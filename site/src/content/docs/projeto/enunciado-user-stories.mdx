**Dias 2 a 5.** O catálogo de user stories que o banco quer. São mais do que consegues fazer: decide o que entra no teu plano.

Usa o que aprendeste em: [ASP.NET Core e Web API](../../dotnet/asp-net-core-e-web-api/), [Entity Framework Core](../../dotnet/entity-framework-core/), [Testes unitários](../../dotnet/testes-unitarios/), [Hands-on II: autorização](../../auth/hands-on-ii-autorizacao/).

## Regras

- Há mais user stories do que tempo. Não as tentes fazer todas: lê o enunciado até ao fim, estima e escolhe (Introdução ao Projeto Final).
- Cada user story segue a mesma receita: regra no domain, caso de uso na application, repositório e migration na infrastructure, controller e dtos na api, testes e pedido no Bruno.
- Todos os pedidos são POST, com os parâmetros no corpo JSON (RPC). O id do cliente vem sempre do token, nunca do pedido. Dinheiro é decimal com precisão (18,2) e as datas guardam-se em UTC.
- A API é RPC: responde sempre HTTP 200 e o resultado vai no Response (success, data, errors). Os erros esperados devolvem-se com Error.NotFound, Error.Conflict, etc.; os erros de regras do Domain lançam DomainException.
- Convenção do projeto: tudo são classes (sem records), uma classe por ficheiro e uma responsabilidade por classe.
- Uma user story só está pronta com testes e um pedido na coleção do Bruno.
- Se ficares bloqueado, abre a user story: tem uma pista de abordagem, sem a solução.

## F1 · Gestão de contas

Abrir, consultar e fechar as contas do cliente.

### US1 · Abrir conta adicional

Como cliente autenticado, quero abrir uma conta nova para separar o meu dinheiro.

**Pedido:** `POST /api/accounts/open`  
**Valor de negócio:** Alto  
**Estimativa:** 3 pontos

```json title="Corpo do pedido"
{ "initialDeposit": 100.00 }
```

**Regras**

- O número da conta é gerado pelo sistema e é único
- O depósito inicial não pode ser negativo
- Um cliente tem no máximo 5 contas ativas
- O cliente vem do token, nunca do corpo do pedido

| Resultado | Quando |
| --- | --- |
| success | Conta criada, com o número da conta nova em data |
| validation | Depósito inicial negativo |
| unauthorized | Sem token válido |
| conflict | Já tem 5 contas ativas |

**Critérios de aceitação**

- [ ] A regra das 5 contas está no Domain ou no handler, e sei explicar porquê
- [ ] A resposta traz o número da conta criada
- [ ] Há testes ao limite (4, 5 e 6 contas)
- [ ] O pedido está na coleção do Bruno

<details>
<summary>Pista de abordagem</summary>

Pensa onde vive a regra «máximo de 5 contas». Se está no Customer (por exemplo, um método OpenAccount), o Domain protege-se a si próprio. Se está no handler, tens de repetir a verificação em todos os sítios que abram contas.

:::tip[Experimenta]
Escreve primeiro o teste que falha com a sexta conta e só depois a implementação.
:::

</details>

### US2 · Consultar contas

Como cliente, quero ver as minhas contas e o detalhe de cada uma.

**Pedido:** `POST /api/accounts/list  ·  POST /api/accounts/get`  
**Valor de negócio:** Alto  
**Estimativa:** 2 pontos  
**Depende de:** US1

```json title="Corpo do pedido"
{ "status": "Active" }
```

**Regras**

- Só devolve contas do cliente autenticado
- Uma conta de outro cliente responde not\_found, igual a uma conta inexistente
- Filtro opcional status (Active ou Closed), enviado no corpo
- O detalhe (get) recebe o número da conta no corpo: \{ "number": "AC-123456" \}
- Ordenado por número

| Resultado | Quando |
| --- | --- |
| success | Lista ou detalhe da conta |
| unauthorized | Sem token válido |
| not\_found | A conta não existe ou não é do cliente |

**Critérios de aceitação**

- [ ] Não é possível ver contas de outro cliente (testado)
- [ ] O filtro por estado é feito na base de dados, não em memória
- [ ] Usa AsNoTracking nas consultas
- [ ] Os pedidos estão na coleção do Bruno

<details>
<summary>Pista de abordagem</summary>

Responder not\_found em vez de forbidden para contas de outros clientes evita revelar que o número existe. O filtro construído com IQueryable só vai à base de dados no fim, por isso podes acrescentar o Where apenas quando o parâmetro vier preenchido.

:::caution[Armadilha]
Chamar ToList antes do Where traz todas as contas de todos os clientes para memória.
:::

</details>

### US3 · Fechar conta

Como cliente, quero fechar uma conta que já não uso.

**Pedido:** `POST /api/accounts/close`  
**Valor de negócio:** Médio  
**Estimativa:** 3 pontos  
**Depende de:** US1

```json title="Corpo do pedido"
{ "number": "AC-123456" }
```

**Regras**

- Só se o saldo for zero
- Uma conta já fechada não pode voltar a ser fechada
- Fechar não apaga: o estado passa a Closed
- Não pode fechar a última conta ativa

| Resultado | Quando |
| --- | --- |
| success | Conta fechada |
| unauthorized | Sem token válido |
| not\_found | A conta não existe ou não é do cliente |
| conflict | Saldo diferente de zero, já fechada ou última conta ativa |

**Critérios de aceitação**

- [ ] A mudança de estado é um método da entidade Account
- [ ] Cada uma das três regras tem um teste
- [ ] O dashboard deixa de mostrar a conta fechada
- [ ] O pedido está na coleção do Bruno

<details>
<summary>Pista de abordagem</summary>

O estado só deve mudar por um método da própria Account (por exemplo, Close), que valida as regras. Assim, nenhum handler consegue fechar uma conta com saldo.

</details>

## F2 · Movimentos e extratos

Depósitos, levantamentos, transferências e tudo o que se consulta sobre eles.

### US4 · Depósito

Como cliente, quero depositar dinheiro numa das minhas contas.

**Pedido:** `POST /api/accounts/deposit`  
**Valor de negócio:** Alto  
**Estimativa:** 3 pontos  
**Depende de:** US1

```json title="Corpo do pedido"
{ "number": "AC-123456", "amount": 250.00, "description": "Salary" }
```

**Regras**

- Nova entidade Transaction: tipo, valor, saldo depois do movimento, descrição e data (UTC)
- O valor tem de ser maior que zero e ter no máximo duas casas decimais
- A conta tem de estar ativa
- O saldo e a Transaction são gravados juntos, numa só chamada a SaveChanges

| Resultado | Quando |
| --- | --- |
| success | Movimento criado, com o novo saldo |
| validation | Valor inválido |
| unauthorized | Sem token válido |
| not\_found | A conta não existe ou não é do cliente |
| conflict | Conta fechada |

**Critérios de aceitação**

- [ ] A entidade Transaction tem configuração e migration
- [ ] Account.Deposit atualiza o saldo e o handler cria a Transaction
- [ ] Há Theory para os valores inválidos (0, negativo, três casas)
- [ ] O pedido está na coleção do Bruno

<details>
<summary>Pista de abordagem</summary>

Pensa em quem cria a Transaction: o método Deposit da conta pode devolvê-la, para garantir que o saldo e o movimento nunca ficam desalinhados. O campo BalanceAfter permite reconstruir o extrato sem recalcular tudo.

:::caution[Armadilha]
Fazer duas gravações separadas (saldo e movimento). Se a segunda falhar, ficas com dinheiro sem movimento.
:::

</details>

### US5 · Levantamento

Como cliente, quero levantar dinheiro de uma das minhas contas.

**Pedido:** `POST /api/accounts/withdraw`  
**Valor de negócio:** Alto  
**Estimativa:** 5 pontos  
**Depende de:** US4

```json title="Corpo do pedido"
{ "number": "AC-123456", "amount": 80.00, "description": "ATM" }
```

**Regras**

- As regras de valor e de conta ativa do depósito aplicam-se aqui
- Não pode ficar com saldo negativo: erro conflict próprio («Insufficient funds»)
- Limite diário de 500 € por conta, somando os levantamentos do dia (UTC)
- A soma do dia é calculada na base de dados

| Resultado | Quando |
| --- | --- |
| success | Movimento criado, com o novo saldo |
| validation | Valor inválido |
| unauthorized | Sem token válido |
| not\_found | A conta não existe ou não é do cliente |
| conflict | Saldo insuficiente, limite diário ou conta fechada |

**Critérios de aceitação**

- [ ] O saldo insuficiente é devolvido como Response.Fail, sem lançar exceção
- [ ] O limite diário usa SumAsync na base de dados
- [ ] Há testes ao limite exato (500 permitido, 500,01 recusado)
- [ ] O pedido está na coleção do Bruno

<details>
<summary>Pista de abordagem</summary>

Para o limite diário precisas de uma consulta ao repositório (por exemplo, a soma dos levantamentos de hoje). Define esse método no contrato da Application e implementa-o na Infrastructure com Where e SumAsync.

:::tip[Experimenta]
Faz dois levantamentos de 300 € seguidos e confirma que o segundo é recusado.
:::

</details>

### US6 · Limites por conta

Como cliente, quero definir o meu limite diário de levantamentos.

**Pedido:** `POST /api/accounts/set-daily-limit`  
**Valor de negócio:** Baixo  
**Estimativa:** 3 pontos  
**Depende de:** US5

```json title="Corpo do pedido"
{ "number": "AC-123456", "dailyWithdrawal": 300.00 }
```

**Regras**

- Por omissão é 500 €
- Tem de estar entre 50 € e 2 000 €
- A US5 passa a usar o limite da conta em vez do valor fixo
- Baixar o limite aplica-se logo; subir só tem efeito no dia seguinte

| Resultado | Quando |
| --- | --- |
| success | Limite alterado |
| validation | Fora dos valores permitidos |
| unauthorized | Sem token válido |
| not\_found | Conta inexistente ou de outro cliente |

**Critérios de aceitação**

- [ ] Há migration para o novo campo, com valor por omissão
- [ ] A regra «subir só no dia seguinte» tem teste
- [ ] A US5 continua a passar nos testes

<details>
<summary>Pista de abordagem</summary>

Acrescentar uma coluna a uma tabela com dados exige um valor por omissão na migration. Lê a migration que o EF gera antes de a aplicar.

</details>

### US7 · Transferência entre contas

Como cliente, quero transferir dinheiro de uma das minhas contas para outra conta do banco.

**Pedido:** `POST /api/transfers/create`  
**Valor de negócio:** Alto  
**Estimativa:** 5 pontos  
**Depende de:** US5

```json title="Corpo do pedido"
{ "fromAccount": "AC-123456", "toAccount": "AC-654321", "amount": 50.00, "description": "Rent" }
```

**Regras**

- A origem tem de ser do cliente autenticado; o destino pode ser de qualquer cliente
- Origem e destino têm de ser diferentes e ambos ativos
- As regras de saldo e de limite diário da origem aplicam-se
- Cria duas Transaction (saída e entrada) e grava tudo numa só chamada a SaveChanges
- Se algo falhar, nada é gravado

| Resultado | Quando |
| --- | --- |
| success | Transferência feita, com o novo saldo da origem |
| validation | Valor inválido ou contas iguais |
| unauthorized | Sem token válido |
| not\_found | Origem não é do cliente ou destino não existe |
| conflict | Saldo insuficiente, limite diário ou conta fechada |

**Critérios de aceitação**

- [ ] Os dois movimentos e os dois saldos mudam na mesma gravação
- [ ] Há um teste que prova que, se a regra falha, nenhum saldo muda
- [ ] O destino inexistente devolve o erro not\_found
- [ ] O pedido está na coleção do Bruno

<details>
<summary>Pista de abordagem</summary>

O SaveChangesAsync grava tudo o que o DbContext está a acompanhar numa única transação. Se carregares as duas contas e alterares os dois saldos antes de gravar, ou grava tudo ou não grava nada. Reutiliza os métodos de depósito e levantamento das entidades.

:::caution[Armadilha]
Gravar a origem e depois o destino em chamadas separadas. Se a segunda falhar, o dinheiro desaparece.
:::

</details>

### US16 · Pedido de empréstimo

Como cliente, quero pedir um empréstimo e acompanhar o estado.

**Pedido:** `POST /api/loans/request  ·  POST /api/loans/list  ·  POST /api/loans/cancel`  
**Valor de negócio:** Médio  
**Estimativa:** 5 pontos  
**Depende de:** US4, US15

```json title="Corpo do pedido"
{ "amount": 10000.00, "months": 24, "accountNumber": "AC-123456" }
```

**Regras**

- Nova entidade Loan, com estados Pending e Cancelled
- Cada cliente só pode ter um pedido Pending
- O cliente só vê e cancela os seus pedidos
- Um pedido cancelado não volta a Pending
- O pedido guarda o valor, o prazo, a conta e a taxa em vigor

| Resultado | Quando |
| --- | --- |
| success | Pedido criado |
| success | Lista dos meus pedidos |
| success | Pedido cancelado |
| unauthorized | Sem token válido |
| not\_found | Pedido inexistente ou de outro cliente |
| conflict | Já há um pedido pendente ou o pedido já foi cancelado |

**Critérios de aceitação**

- [ ] Há teste ao segundo pedido pendente
- [ ] O cliente não vê pedidos de outros
- [ ] Transições de estado com testes
- [ ] Pedidos na coleção do Bruno

<details>
<summary>Pista de abordagem</summary>

As transições de estado (Pending → Cancelled) devem ser métodos da entidade Loan, tal como o Close da Account. Assim o handler não consegue aprovar um pedido já rejeitado.

### US18 · Refresh token

Como cliente, quero manter a sessão sem voltar a escrever a password.

**Pedido:** `POST /api/auth/refresh`  
**Valor de negócio:** Médio  
**Estimativa:** 5 pontos

```json title="Corpo do pedido"
{ "refreshToken": "a1b2c3..." }
```

**Regras**

- O Login passa a devolver também um refresh token aleatório com validade de 7 dias
- Guarda-se apenas o hash do refresh token, numa nova entidade RefreshToken
- Cada refresh troca o token por um novo e invalida o antigo (rotation)
- Reutilizar um refresh token antigo revoga todas as sessões do cliente

| Resultado | Quando |
| --- | --- |
| success | Novo access token e novo refresh token |
| unauthorized | Refresh token inválido, expirado ou revogado |

**Critérios de aceitação**

- [ ] O refresh token tem pelo menos 32 bytes aleatórios
- [ ] Nenhum refresh token está em claro na base de dados
- [ ] Há teste à reutilização de um token antigo
- [ ] Pedidos na coleção do Bruno

<details>
<summary>Pista de abordagem</summary>

O refresh token não é um JWT mas sim um valor aleatório, que só tem significado no teu servidor. Para o guardar com hash, usa um hash rápido e determinístico (SHA-256): precisas de o procurar por valor, e a sua aleatoriedade já impede os ataques de dicionário.

:::caution[Armadilha]
Guardar o refresh token em claro. Quem ler a base de dados passa a ter todas as sessões.
:::

</details>

<summary>User story completa para o Azure DevOps</summary>


```markdown title="Descrição"
Como cliente autenticado, quero manter a sessão sem voltar a escrever a password, para usar a aplicação sem interrupções e com segurança.

O login devolve também um refresh token aleatório. Cada refresh troca o token por um novo (rotation) e a reutilização de um token antigo revoga todas as sessões do cliente.

**Regras de negócio**
```

### US19 · Logout

Como cliente, quero terminar a sessão, para que ninguém a possa reutilizar.

**Pedido:** `POST /api/auth/logout`  
**Valor de negócio:** Médio  
**Estimativa:** 2 pontos  
**Depende de:** US18

```json title="Corpo do pedido"
{ "refreshToken": "a1b2c3..." }
```

**Regras**

- Recebe o refresh token da sessão a terminar
- Apaga esse refresh token, sem afetar as sessões dos outros dispositivos
- O access token continua válido até expirar
- Repetir o logout com o mesmo token não é erro: responde success
- Usa a entidade RefreshToken da US18

| Resultado | Quando |
| --- | --- |
| success | Sessão terminada |
| validation | Pedido sem refresh token |

**Critérios de aceitação**

- [ ] Depois do logout, o refresh token deixa de funcionar
- [ ] As outras sessões do cliente continuam ativas
- [ ] Há teste ao logout repetido
- [ ] Pedido na coleção do Bruno

<details>
<summary>Pista de abordagem</summary>

O access token é um JWT sem estado: o servidor não o consegue apagar. Por isso o logout só impede a renovação, e o access token acaba por expirar sozinho. Pensa porque é que o access token deve ter validade curta.

</details>

### US20 · Limitar tentativas de login

Como banco, quero travar quem tenta adivinhar passwords.

**Pedido:** `POST /api/auth/login (alteração)`  
**Valor de negócio:** Médio  
**Estimativa:** 5 pontos

**Regras**

- Após 5 falhas em 15 minutos, o email fica bloqueado durante 15 minutos
- Devolve o erro rate\_limited com o tempo de espera na mensagem
- Um login certo repõe o contador
- As falhas gravam-se por email, também para emails que não existem
- A resposta continua igual para email desconhecido e password errada

| Resultado | Quando |
| --- | --- |
| success | Login certo |
| unauthorized | Credenciais inválidas |
| rate\_limited | Demasiadas tentativas |

**Critérios de aceitação**

- [ ] O bloqueio funciona também para emails inexistentes
- [ ] A janela e o limite vêm de configuração
- [ ] Testes às fronteiras (4.ª, 5.ª e 6.ª tentativas)

<details>
<summary>Pista de abordagem</summary>

Se só contares falhas de emails que existem, um atacante descobre que emails estão registados pela diferença de comportamento. Conta todas as falhas.

</details>
