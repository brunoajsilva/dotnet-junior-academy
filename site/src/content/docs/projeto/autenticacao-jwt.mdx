## Como funciona o token JWT

No login, a API devolve um token assinado. O cliente envia-o em cada pedido, no cabeçalho Authorization. A API valida a assinatura e a validade, e fica a saber quem fez o pedido sem ir à base de dados.

```bash title="Um JWT descodificado"
# header
{ "alg": "HS256", "typ": "JWT" }

# payload (the claims)
{
  "sub": "1",
  "email": "ana@example.com",
  "name": "Ana Pereira",
  "exp": 1793700000,
  "iss": "BankingApp",
  "aud": "BankingApp.Clients"
}

# signature = HMACSHA256(header + "." + payload, Jwt:Key)
# anyone can READ the payload (base64): never put secrets in it
```

## Pacotes e configuração do JWT

O token é assinado com uma chave que fica no appsettings.json, na secção Jwt. Para a formação, é a forma mais simples: uma chave de desenvolvimento, que muda de cada vez que quiseres. Num projeto real, esta chave seria um segredo fora do repositório (variável de ambiente ou cofre), mas isso fica para outro dia.

1. Instalar os pacotes do JWT e do hash de passwords
2. Acrescentar a secção Jwt ao appsettings.json, com a Key (pelo menos 32 caracteres)

```bash title="Instalar dependências"
dotnet add src/BankingApp.Api            package Microsoft.AspNetCore.Authentication.JwtBearer
dotnet add src/BankingApp.Infrastructure package System.IdentityModel.Tokens.Jwt
dotnet add src/BankingApp.Infrastructure package Microsoft.Extensions.Identity.Core
dotnet add src/BankingApp.Infrastructure package Microsoft.Extensions.Options.ConfigurationExtensions
```

## Bruno: configurar o Authorize passo a passo

O Bruno guarda a coleção em ficheiros de texto (.bru), que podes pôr no repositório, em docs/bruno. O fluxo é fazer Login, guardar o token numa variável e usá-lo como Bearer Token.

- **Instalar e criar a coleção**: Instala o Bruno (usebruno.com). Em Collections escolhe Create Collection, dá-lhe o nome BankingApp e guarda-a numa pasta do repositório, por exemplo docs/bruno.
- **Criar o ambiente Local**: No canto superior direito, abre o seletor de ambientes e escolhe Configure. Cria o ambiente Local com a variável baseUrl, com o endereço https com que a Api arranca (está no launchSettings.json). Depois seleciona o ambiente Local.
- **Pedido Register (anónimo)**: New Request, método POST, URL \{\{baseUrl\}\}/api/auth/register. No separador Body escolhe JSON e escreve o corpo. O separador Auth fica em No Auth. Envia: esperas HTTP 200 com success true.
- **Pedido Login e guardar o token**: Novo pedido POST \{\{baseUrl\}\}/api/auth/login com email e password. No separador Vars, secção Post Response, acrescenta a variável token com o valor res.body.data.accessToken (o token vem dentro de data). Cada vez que fizeres Login, o token novo fica guardado.
- **Pedido RetrieveDashboard (autenticado)**: Novo pedido POST \{\{baseUrl\}\}/api/dashboard/retrieve, com o corpo JSON \{\}. No separador Auth escolhe Bearer Token e escreve \{\{token\}\} no campo Token. O Bruno envia o cabeçalho Authorization: Bearer \<token\>.
- **Experimentar os dois resultados**: Corre o Login e depois o RetrieveDashboard: esperas success true com as contas em data. Muda o Auth do RetrieveDashboard para No Auth e envia outra vez: continua a ser HTTP 200, mas com success false e o erro unauthorized. Isso prova que o \[Authorize\] está a funcionar.
- **Se der erro de certificado**: Em desenvolvimento, o certificado HTTPS é local. Na primeira execução o IDE pergunta se queres confiar nele: aceita. Se o Bruno continuar a recusar, desativa a verificação do certificado SSL nas preferências (só em desenvolvimento).
- **Opcional: autenticação ao nível da coleção**: Nas definições da coleção, separador Auth, escolhe Bearer Token com \{\{token\}\}. Nos pedidos que precisam de token, põe o modo Inherit. Evita repetir a configuração em cada pedido.

## Verificar

Confirma os cinco casos antes de avançares.

1. POST /api/auth/register válido: success true com o número da primeira conta
2. Repetir o Register com o mesmo email e NIF: success false com dois erros conflict
3. POST /api/auth/login com password errada: success false, erro unauthorized
4. POST /api/dashboard/retrieve sem token: success false, erro unauthorized (e HTTP 200)
5. POST /api/dashboard/retrieve com o token do Login: success true com uma conta e saldo 0

(todos com HTTP 200)

<summary>Saber mais</summary>

Este passo aplica, na BankingApp, o que fizeste no AuthLab. O JWT (JSON Web Token) é o formato do token; o esquema Bearer, usado no cabeçalho Authorization, é a forma de o enviar. A própria API emite o token, em vez de um servidor de identidade externo. Num banco real usar-se-ia um servidor de identidade; aqui aprendes a base.

A password nunca é guardada: guarda-se o hash. O token só prova quem és até expirar (ExpiresMinutes), por isso é curto.

:::caution[Armadilha]
Usar a chave de formação num projeto real. Quem tiver a chave consegue fabricar tokens válidos para qualquer cliente, por isso em produção ela vem de um cofre ou de uma variável de ambiente.
:::

:::tip[Experimenta]
Copia o token do Login para jwt.io e vê os claims. Percebe porque nunca se põem segredos no payload.
:::

</details>
