## Criar a solução, os projetos e as referências

Convenção do projeto inteiro: tudo são classes (sem records), uma classe por ficheiro, e cada classe com uma única responsabilidade. A solução e os projetos criam-se no IDE (Visual Studio ou VS Code), sem linha de comandos. As referências entre projetos são a arquitetura: se o Domain não referencia nada, ninguém o consegue contaminar com EF Core. Os únicos comandos deste passo instalam dependências.

1. Criar a solução BankingApp, com as pastas src e tests
2. Criar os cinco projetos: Domain, Application e Infrastructure (Class Library), Api (ASP.NET Core Web API com controllers, .NET 10) e Tests (xUnit)
3. Configurar as Project References segundo a regra das dependências
4. Apagar os ficheiros de exemplo dos templates (Class1, WeatherForecast e UnitTest1)
5. Instalar os pacotes NuGet, a UI do Swagger e a ferramenta dotnet-ef
6. Compilar a solução (Build Solution)

```csharp title="BankingApp.Domain/Customers/Customer.cs"
using BankingApp.Domain.Common;

namespace BankingApp.Domain.Customers;

public class Customer
{
    private Customer() { }   // required by EF Core

    public Customer(string name, string taxId)
    {
        if (string.IsNullOrWhiteSpace(name))
            throw new DomainException("Name is required.");
        if (taxId.Length != 9 || !taxId.All(char.IsDigit))
            throw new DomainException($"Invalid tax id: {taxId}");

        Name = name.Trim();
        TaxId = taxId;
    }

    public int Id { get; private set; }
    public string Name { get; private set; } = "";
    public string TaxId { get; private set; } = "";
}
```

## Application: a abstração de entrada e de saída (API RPC)

Esta API é RPC: o HTTP é só o transporte. Todos os pedidos são POST, para /api/\<área\>/\<ação\> (por exemplo, /api/accounts/deposit), e os parâmetros vão sempre no corpo JSON, nunca na rota nem na query string. Se o pedido chegou ao servidor e foi processado, a resposta é sempre 200 OK, e o resultado vem no corpo. Para isso, todos os casos de uso recebem um Request e devolvem um Response, que tem uma lista de erros. Quem chama lê success e errors em vez do código HTTP. Criamos já estas peças, porque tudo o que vem a seguir as usa.

1. Criar o Error, com uma fábrica por tipo (validation, not\_found, conflict, unauthorized, forbidden)
2. Criar a classe base Request, de onde herdam todos os comandos e consultas
3. Criar o Response\<T\>: success é «não há erros»; Data guarda o resultado; Empty é para os casos de uso sem dados
4. Criar o IHandler\<TRequest, TData\>, o contrato de qualquer caso de uso

```csharp title="BankingApp.Application/Common/Error.cs"
namespace BankingApp.Application.Common;

// RPC: errors are data. Every use case answers with a list of Error, never with an HTTP code.
public class Error
{
    public Error(string code, string message)
    {
        Code = code;
        Message = message;
    }

    public string Code { get; }
    public string Message { get; }

    public static Error Validation(string message)   => new("validation", message);
    public static Error NotFound(string message)     => new("not_found", message);
    public static Error Conflict(string message)     => new("conflict", message);
    public static Error Unauthorized(string message) => new("unauthorized", message);
    public static Error Forbidden(string message)    => new("forbidden", message);
    public static Error Unexpected()                 => new("unexpected", "Unexpected error.");
}
```

```csharp title="BankingApp.Application/Common/Request.cs"
namespace BankingApp.Application.Common;

// every input of a use case (command or query) derives from Request
public abstract class Request
{
}
```

```csharp title="BankingApp.Application/Common/Response.cs"
namespace BankingApp.Application.Common;

// the output of EVERY use case: success is just "no errors"
public class Response<T>
{
    public bool Success => Errors.Count == 0;
    public T? Data { get; init; }
    public IReadOnlyList<Error> Errors { get; init; } = [];

    public static Response<T> Ok(T data) => new() { Data = data };

    public static Response<T> Fail(params IEnumerable<Error> errors)
        => new() { Errors = errors.ToList() };

    // convert the data (for example, a result into a DTO) and keep the errors
    public Response<TOut> Map<TOut>(Func<T, TOut> map)
        => Success ? Response<TOut>.Ok(map(Data!)) : Response<TOut>.Fail(Errors);
}
```


```csharp title="BankingApp.Application/Abstractions/IHandler.cs"
using BankingApp.Application.Common;

// one handler per use case: a Request goes in, a Response comes out
public interface IHandler<in TRequest, TData> where TRequest : Request
{

}
```

## Application: contratos e o primeiro caso de uso

A Application define o que precisa (ICustomerRepository) e escreve cada caso de uso em três classes pequenas, cada uma no seu ficheiro: ficam todas juntas na pasta do caso de uso, dentro de Handlers/CommandHandlers (comandos) ou de Handlers/QueryHandlers (consultas), por exemplo Handlers/CommandHandlers/CreateCustomer. A pasta Handlers agrupa os dois. Um handler recebe um Request e devolve um Response: os erros de negócio devolvem-se, não se lançam. Não sabe nada de EF Core nem de HTTP.

```csharp title="BankingApp.Application/Handlers/CommandHandlers/CreateCustomer/CreateCustomerHandler.cs"
using BankingApp.Application.Abstractions;
using BankingApp.Application.Common;
using BankingApp.Domain.Customers;

namespace BankingApp.Application.Handlers.CommandHandlers.CreateCustomer;

// handler: the use case. Business errors come back in the Response, they are not thrown
public class CreateCustomerHandler : IHandler<CreateCustomerCommand, CustomerResult>
{
    private readonly ICustomerRepository _customers;

    public CreateCustomerHandler(ICustomerRepository customers) => _customers = customers;

    public async Task<Response<CustomerResult>> HandleAsync(CreateCustomerCommand request, CancellationToken ct)
    {
        if (await _customers.ExistsByTaxIdAsync(request.TaxId, ct))
            return Response<CustomerResult>.Fail(
                Error.Conflict($"A customer with tax id {request.TaxId} already exists."));

        var customer = new Customer(request.Name, request.TaxId);

        await _customers.AddAsync(customer, ct);
        await _customers.SaveChangesAsync(ct);

        return Response<CustomerResult>.Ok(CustomerResult.From(customer));
    }
}
```

```csharp title="BankingApp.Api/Controllers/CustomersController.cs"
using BankingApp.Api.Contracts.Customers;
using BankingApp.Application.Abstractions;
using BankingApp.Application.Common;
using BankingApp.Application.Handlers.CommandHandlers.CreateCustomer;
using BankingApp.Application.Handlers.QueryHandlers.ListCustomers;
using Microsoft.AspNetCore.Mvc;

namespace BankingApp.Api.Controllers;

[ApiController]
[Route("api/[controller]")]
public class CustomersController : ControllerBase
{
    private readonly IHandler<CreateCustomerCommand, CustomerResult> _create;
    private readonly IHandler<ListCustomersQuery, IReadOnlyList<CustomerResult>> _list;

    public CustomersController(
        IHandler<CreateCustomerCommand, CustomerResult> create,
        IHandler<ListCustomersQuery, IReadOnlyList<CustomerResult>> list)
    {
        _create = create;
        _list = list;
    }

    // RPC: every operation is a POST to /api/<area>/<action>, and the answer is always 200 OK.
    // Read "success" and "errors" in the body.
    [HttpPost("list")]
    public async Task<Response<IEnumerable<CustomerResponse>>> List(CancellationToken ct)
    {
        var result = await _list.HandleAsync(new ListCustomersQuery(), ct);
        return result.Map(items => items.Select(CustomerResponse.From));
    }

    [HttpPost("create")]
    public async Task<Response<CustomerResponse>> Create(NewCustomer body, CancellationToken ct)
    {
        var result = await _create.HandleAsync(new CreateCustomerCommand { Name = body.Name, TaxId = body.TaxId }, ct);
        return result.Map(CustomerResponse.From);
    }
}
```

```csharp title="BankingApp.Api/Responses/ValidationResponse.cs"
using BankingApp.Application.Common;
using Microsoft.AspNetCore.Mvc;

namespace BankingApp.Api.Responses;

public static class ValidationResponse
{
    // [ApiController] would answer 400 + ProblemDetails when the DTO is invalid.
    // In an RPC API, we answer 200 and put every invalid field in the errors list.
    public static IActionResult Create(ActionContext context)
    {
        var errors = context.ModelState
            .Where(entry => entry.Value is { Errors.Count: > 0 })
            .SelectMany(entry => entry.Value!.Errors
                .Select(e => Error.Validation($"{entry.Key}: {e.ErrorMessage}")))
            .ToList();

        return new OkObjectResult(Response<object>.Fail(errors));
    }
}
```

```csharp title="BankingApp.Api/Middleware/ExceptionMiddleware.cs"
using BankingApp.Application.Common;
using BankingApp.Domain.Common;

namespace BankingApp.Api.Middleware;

public class ExceptionMiddleware
{
    private readonly RequestDelegate _next;
    private readonly ILogger<ExceptionMiddleware> _logger;

    public ExceptionMiddleware(RequestDelegate next, ILogger<ExceptionMiddleware> logger)
    {
        _next = next;
        _logger = logger;
    }

    public async Task InvokeAsync(HttpContext context)
    {
        try
        {
            await _next(context);
        }
        catch (Exception ex)
        {
            Error error;

            if (ex is DomainException)
            {
                error = Error.Validation(ex.Message);   // a rule of the Domain refused the data
            }
            else
            {
                _logger.LogError(ex, "Unhandled error on {Path}", context.Request.Path);
                error = Error.Unexpected();              // never leak the details to the client
            }

            // RPC: the call reached the server, so the HTTP answer is always 200
            context.Response.StatusCode = StatusCodes.Status200OK;
            await context.Response.WriteAsJsonAsync(Response<object>.Fail(error));
        }
    }
}

// An exception is for the unexpected. Expected errors (not found, conflict)
// are returned by the handlers, as Response.Fail(...).
```

```csharp title="BankingApp.Api/Program.cs"
using BankingApp.Api.Middleware;
using BankingApp.Api.Responses;
using BankingApp.Application;
using BankingApp.Infrastructure;

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddControllers()
    .ConfigureApiBehaviorOptions(o =>
        o.InvalidModelStateResponseFactory = ValidationResponse.Create);   // invalid DTO -> 200 + errors
builder.Services.AddOpenApi();
builder.Services.AddApplication();
builder.Services.AddInfrastructure(builder.Configuration);

var app = builder.Build();

app.UseMiddleware<ExceptionMiddleware>();   // first: catches everything below

if (app.Environment.IsDevelopment())
{
    app.MapOpenApi();                        // /openapi/v1.json
```

## Correr e verificar

A aplicação está funcional quando consegues criar e listar clientes pelo Swagger UI e ver a linha na base de dados. Repara que todas as respostas são 200: o que muda é o corpo.

1. Correr a BankingApp.Api no IDE (F5) e abrir /swagger
2. POST /api/customers/create com um cliente válido: 200 com success true
3. Repetir o POST: 200 com success false e o erro conflict
4. POST com NIF "123": 200 com success false e o erro validation
5. POST /api/customers/list e confirmar a linha na tabela Customers (cliente SQL)
